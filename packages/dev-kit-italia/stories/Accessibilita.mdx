# Accessibilità

Questa guida estende il [fondamento Accessibilità del design system .italia](https://designers.italia.it/design-system/fondamenti/accessibilita/) documentando come si comportano alcuni dei principali strumenti di verifica automatica nell'analizzare pagine realizzate con web component Dev Kit Italia.

Dev Kit Italia adotta un [approccio HTML-first con slot](/?path=/docs/documentazione-tecnica--documentazione): il contenuto significativo vive nel light DOM, il componente lo proietta nel shadow DOM e l'accessibility tree del browser lo espone alle tecnologie assistive. Alcuni strumenti di verifica attraversano correttamente il shadow DOM, altri lo ignorano, altri producono falsi positivi.

I tool automatici rilevano solo una parte degli errori di accessibilità: molti criteri WCAG richiedono valutazione umana. I controlli manuali sono sempre necessari e per flussi critici è indispensabile coinvolgere esperti di accessibilità e, ove necessario, utenti reali. Vedi la sezione [Verifiche manuali](#verifiche-manuali) per le indicazioni specifiche sui web component.

I risultati che seguono riguardano i tool testati al momento della stesura (axe-core v4.11.1, Siteimprove v2.0, ARC Toolkit v5.7.10, WAVE 3.2.7.1, MAUVE++ 4.0.2) su questi componenti: Accordion, Breadcrumbs, Button, Callout, Card, Checkbox, Chip, Dropdown, Hero, Input, Modal, Radio button, Select. La [pagina di test dedicata](https://italia.github.io/design-jekyll-devkit-theme/test-a11y/) e questa guida potranno essere integrate nel tempo con nuovi componenti, casi di test e tool aggiuntivi.

**Feedback e contributi**: [apri una segnalazione](https://github.com/italia/dev-kit-italia/issues) su `italia/dev-kit-italia`.

Tool automatico più affidabile tra quelli testati è **axe-core**, classificando casi di test corretti ed errori reali. Per una copertura più ampia durante lo sviluppo, combinarlo con **pa11y con axe runner** e/o **Siteimprove**.

### Per CLI e CI/CD

```bash
npx pa11y <url> --standard WCAG2AA --runner axe
```

Esempio di configurazione `.pa11yci`:

```json
{
  "defaults": {
    "runner": "axe",
    "standard": "WCAG2AA",
    "ignore": []
  },
  "urls": [
    "https://example-pa-site.gov.it/",
    "https://example-pa-site.gov.it/contatti"
  ]
}
```

Aggiungere all'ignore list gli eventuali falsi positivi se documentati, ad esempio `list` per i breadcrumbs. Verificare periodicamente caso per caso che le regole ignorate siano effettivamente falsi positivi.

## Slot obbligatori

Quando uno slot che alimenta un elemento semantico non è popolato, il componente genera un nodo accessibile con nome vuoto nell'accessibility tree — un heading `""` o una label `""`. Il kit segnala il problema nella console del browser (esempio di messaggio: `[it-card] no title slot content found`). Questi warning di sviluppo vanno trattati come errori in CI.

## Falsi positivi noti

Alcuni tool segnalano errori su componenti correttamente implementati. I casi documentati di seguito non corrispondono a problemi reali e non richiedono azioni correttive. La lista non è esaustiva ma da considerare esempio e guida. 

### ARC Toolkit

ARC Toolkit entra nel shadow DOM ma non risolve correttamente la proiezione degli slot. Con componenti **correttamente popolati** segnala molti falsi positivi come:

- `<it-card>` con slot `title`: "heading vuoto" (WCAG 1.3.1)
- `<it-callout>` con slot `title`: "heading vuoto" (WCAG 1.3.1)
- `<it-input>` con slot `label`: errore label (WCAG 1.3.1)
- `<it-button>` con testo: errore button (WCAG 4.1.2)
- `<it-select>` con slot `label`: errore label (WCAG 1.3.1)
- `<it-checkbox>` con slot `label`: errore label (WCAG 1.3.1)

Nella configurazione attuale produce quindi un numero elevato di falsi positivi sui web component Dev Kit Italia, rendendo difficile distinguere errori reali. Non consigliato come tool primario.

### axe-core e pa11y con axe runner: breadcrumbs

`list` e `listitem` segnalati su `<it-breadcrumbs>`. L'accessibility tree è corretto. Falso positivo documentato nella storia del componente al [paragrafo Accessibilità](/?path=/docs/componenti-breadcrumbs--documentazione#accessibilità).

## Limiti strutturali

### ARIA cross-shadow-root

Qualora si usino attributi `it-aria-describedby` o `it-aria-labelledby` su `<it-input>`, questi vengono applicati all'elemento `<input>` generato nel shadow DOM. Tuttavia, se l'ID referenziato appartiene a un elemento nel light DOM esterno allo shadow DOM del componente, la descrizione o la label **non viene annunciata dai lettori di schermo**. È un limite della specifica W3C: questi attributi aria fanno sempre riferimento a ID nello stesso scope DOM. 

Per `<it-input>` Dev Kit Italia mette a disposizione attributi dedicati che generano automaticamente tutti gli attributi necessari dentro lo shadow DOM:
- `support-text`: testo di supporto interno al componente
- `validity-message`: messaggio di validazione
- `custom-validation`: validazione custom

### Tool di verifica senza supporto shadow DOM

Strumenti basati su serializzazione DOM standard **non entrano nel shadow DOM**: 

- Non percepiscono elementi semantici (heading, label, button) e ruoli ARIA generati nel shadow DOM
- Non segnalano errori né componenti implementati correttamente
- Segnalano solo elementi nel light DOM (slot con `style` inline, elementi HTML della pagina)

Una pagina che usa web component Dev Kit Italia è quindi non verificabile con questo tipo di strumenti.

## Verifiche manuali 

Ricorda che le verifiche automatiche non sono sufficienti, molti criteri WCAG richiedono valutazione umana e alcuni tool hanno i limiti specifici sul shadow DOM documentati in questa pagina. Corretta semantica degli elementi, ingrandimento, navigazione da tastiera e lettori di schermo vanno sempre verificati manualmente.

**Combinazioni consigliate:**

Il [fondamento Accessibilità](https://designers.italia.it/design-system/fondamenti/accessibilita/) indica **Windows + Chrome + JAWS** come combinazione di riferimento. Data la relativa novità della tecnologia web component con shadow DOM, verificare su più combinazioni per rilevare comportamenti difformi tra browser e lettori di schermo. Un setup minimo:

Desktop:
- Windows + Chrome o Edge + JAWS o NVDA
- macOS + Chrome o Safari + VoiceOver

Mobile:
- iOS + Safari + VoiceOver
- Android + Chrome + TalkBack

**In aggiunta al [workflow descritto nel fondamento](https://designers.italia.it/design-system/fondamenti/accessibilita/), per i web component:**

1. **Console browser**: durante lo sviluppo, Dev Kit segnala gli slot vuoti obbligatori con warning specifici
2. **Tab Accessibility di Chrome DevTools**: selezionare l'elemento semantico nel shadow DOM del componente (es. `<h3>` dentro `<it-card>`). Verificare `Name`, `Role` e attributi ARIA

## Verifica automatica in Storybook

Storybook integra strumenti di verifica automatica dell'accessibilità per le singole varianti dei componenti.

### Plugin axe

I risultati delle verifiche del plugin axe sono disponibili nel tab "Accessibility" della storia.

### @web/test-runner con a11ySnapshot

Complementare al plugin axe, permetterà di verificare programmaticamente:
- Accessibility tree effettivo
- Navigazione da tastiera con eventi nativi
- Stati dinamici post-interazione
