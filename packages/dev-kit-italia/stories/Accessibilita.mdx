# Accessibilità: verificabilità delle pagine che usano Dev Kit Italia

Questa guida estende il [fondamento Accessibilità del design system .italia](https://designers.italia.it/design-system/fondamenti/accessibilita/) per il contesto di pagine realizzate con Dev Kit Italia documentando come si comportano alcuni dei principali tool di verifica automatica.

Dev Kit Italia adotta un [approccio HTML-first con slot](/?path=/docs/documentazione-tecnica--documentazione): il contenuto significativo vive nel light DOM, il componente lo proietta nel shadow DOM e l'accessibility tree del browser lo espone alle tecnologie assistive. Questo fa sì che i tool di verifica automatica si comportino in modo molto diverso. Alcuni attraversano correttamente il shadow DOM, altri lo ignorano, altri producono falsi positivi. I risultati che seguono riguardano i tool testati al momento della stesura: nuovi tool o versioni future potrebbero comportarsi diversamente.

Ricordati che i tool automatici rilevano solo una parte degli errori di accessibilità. La maggioranza dei criteri di successo WCAG richiedono valutazione umana. I controlli manuali sono sempre necessari e per flussi critici è indispensabile coinvolgere esperti di accessibilità e, ove necessario, testarne l'usabilità con utenti reali. Vedi la sezione [Verifiche manuali](#verifiche-manuali) per le indicazioni specifiche sui web component.

Feedback benvenuti: apri una issue su [italia/dev-kit-italia](https://github.com/italia/dev-kit-italia). L'analisi è basata su questa [pagina di test dedicata](https://italia.github.io/design-jekyll-devkit-theme/test-a11y/).

Tra i tool elencati, **axe-core** è quello che classifica in modo più affidabile sia i `Passes` — componenti correttamente implementati — sia gli errori reali. È il tool consigliato per le verifiche durante lo sviluppo. Per una copertura più ampia, combinarlo con **pa11y con axe runner** o **Siteimprove**.

### Per CI/CD

```bash
npx pa11y <url> --standard WCAG2AA --runner axe
```

Esempio di configurazione `.pa11yci`:

```json
{
  "defaults": {
    "runner": "axe",
    "standard": "WCAG2AA",
    "ignore": []
  },
  "urls": [
    "https://example-pa-site.gov.it/",
    "https://example-pa-site.gov.it/contatti"
  ]
}
```

Aggiungere eventualmente all'ignore list i falsi positivi noti, ad esempio `list` per i breadcrumbs documentato nelle storie. Verificare periodicamente caso per caso che le regole ignorate siano effettivamente falsi positivi.

## Slot obbligatori

## Falsi positivi noti

Alcuni tool segnalano errori su componenti correttamente implementati. I casi documentati di seguito non corrispondono a problemi reali e non richiedono azioni correttive.

### ARC Toolkit: falsi positivi sistematici

ARC Toolkit entra nel shadow DOM ma non risolve correttamente la proiezione degli slot. Con componenti **correttamente popolati** segnala molti falsi positivi come:

- `<it-card>` con slot `title`: "heading vuoto" (WCAG 1.3.1)
- `<it-callout>` con slot `title`: "heading vuoto" (WCAG 1.3.1)
- `<it-input>` con slot `label`: errore label (WCAG 1.3.1)
- `<it-button>` con testo: errore button (WCAG 4.1.2)
- `<it-select>` con slot `label`: errore label (WCAG 1.3.1)
- `<it-checkbox>` con slot `label`: errore label (WCAG 1.3.1)

**Non usarlo come tool principale.** I risultati mescolano errori reali e falsi positivi senza distinzione.

### axe-core e pa11y con axe runner: breadcrumbs

`list` e `listitem` segnalati su `<it-breadcrumbs>`. L'accessibility tree è corretto. Falso positivo documentato nella storia del componente al [paragrafo Accessibilità](/?path=/docs/componenti-breadcrumbs--documentazione#accessibilità).

### pa11y con htmlcs runner: form e attributi

- "Form non contiene submit button" quando il submit è un `<it-button type="submit">`. HTML_CodeSniffer non riconosce il web component.
- Attributo `align` su `<td>` segnalato come HTML 4.01. È un attributo usato internamente dal componente, non eliminabile dal consumer.

### WAVE: contrasto radio group

Falso positivo noto di WAVE su radio group con contrasto 1.4.3.

## Limiti strutturali

### ARIA cross-shadow-root

Quando si usano gli attributi `it-aria-describedby` o `it-aria-labelledby` su `<it-input>`, questi vengono applicati correttamente all'elemento `<input>` generato nel shadow DOM. Tuttavia, se l'ID referenziato appartiene a un elemento nel light DOM esterno al componente, la descrizione o la label **non viene annunciata dai lettori di schermo**. È un limite della specifica W3C: questi attributi fanno sempre riferimento a ID nello stesso scope DOM. Lo stesso limite si applica verosimilmente agli altri componenti form (`<it-select>`, `<it-checkbox>`, `<it-radio>`, ...).

Esempi di attributi da usare nel componente `<it-input>` che funzionano:
- `support-text`: testo di supporto interno al componente
- `validity-message`: messaggio di validazione
- `custom-validation`: validazione custom

La proposta W3C [Cross-root ARIA Delegation](https://github.com/leobalter/cross-root-aria-delegation) affronterebbe questo limite a livello di piattaforma.

### Tool di verifica senza supporto shadow DOM

Strumenti basati su serializzazione DOM standard **non entrano nel shadow DOM**: 

- Non percepiscono elementi semantici (heading, label, button) e ruoli ARIA generati nel shadow DOM
- Non segnalano errori né pass sui componenti
- Segnalano solo elementi nel light DOM (slot con `style` inline, elementi HTML della pagina)

Una pagina che usa web component Dev Kit Italia è quindi non verificabile con questo tipo di strumenti, non necessariamente non conforme.

## Verifiche manuali 

Le verifiche automatiche non sono sufficienti: molti criteri WCAG richiedono valutazione umana, e alcuni tool hanno i limiti specifici sul shadow DOM documentati in questa pagina. Ingrandimento, navigazione da tastiera e lettori di schermo vanno sempre verificati manualmente.

**Combinazioni consigliate:**

Il [fondamento Accessibilità](https://designers.italia.it/design-system/fondamenti/accessibilita/) indica **Windows + Chrome + JAWS** come combinazione di riferimento. Data la relativa novità dei web component, verificare su più combinazioni per rilevare comportamenti difformi tra browser e lettori di schermo. Un setup minimo:

Desktop:
- Windows + Chrome o Edge + JAWS o NVDA
- macOS + Chrome o Safari + VoiceOver

Mobile:
- iOS + Safari + VoiceOver
- Android + Chrome + TalkBack

**In aggiunta al [workflow descritto nel fondamento](https://designers.italia.it/design-system/fondamenti/accessibilita/), per i web component:**

1. **Console browser**: durante lo sviluppo, Dev Kit segnala gli slot vuoti obbligatori con warning specifici.
2. **Tab Accessibility di Chrome DevTools**: selezionare l'elemento semantico nel shadow DOM del componente (es. `<h3>` dentro `<it-card>`). Verificare `Name`, `Role` e attributi ARIA.

## Verifica automatica in Storybook

Storybook integra strumenti di verifica automatica dell'accessibilità per le singole varianti dei componenti.

### Plugin axe

Il plugin axe verifica automaticamente ogni storia. I risultati sono visibili nel tab "Accessibility" presente in ogni storia.

### @web/test-runner con a11ySnapshot

Complementare al plugin axe, permetterà di verificare programmaticamente:
- Accessibility tree effettivo
- Navigazione da tastiera con eventi nativi
- Stati dinamici post-interazione

- [Testing Accessibility with Shadow Roots](https://dev.to/westbrook/testing-accessibility-with-shadow-roots-55cm) — Westbrook Johnson (Adobe Spectrum)
- [Testing Web Components with @web/test-runner](https://open-wc.org/blog/testing-web-components-with-web-test-runner/) — Open Web Components
